# new-idea2

Experiments with training language models locally.

The first experiment is a **character-level transformer trained from scratch** on
Tiny Shakespeare — no pretrained weights, no fine-tuning, and no GPU. The model,
the tokenizer and the training loop are all written here; only the backward pass
(autograd) is taken as given.

## What's here

| File | Purpose |
| --- | --- |
| [`model.py`](model.py) | The transformer: causal self-attention, multi-head projection, pre-norm residual blocks, language-model head |
| [`train.py`](train.py) | Tokeniser, batching, training loop, per-step loss logging, checkpointing and resume, text sampling |
| [`render_curve.py`](render_curve.py) | Renders the loss curve as SVG/HTML using only the standard library |
| [`bigram.py`](bigram.py) | Bigram counting model — the simplest possible LM, used as a comparison floor |
| [`bpe.py`](bpe.py) | Byte-level BPE tokenizer, trained from scratch on the corpus |
| [`chat.py`](chat.py) | Interactive prompt for a trained checkpoint |
| [`serve.py`](serve.py) | Local web prompt: a stdlib server that streams tokens into the browser |
| [`test_all.py`](test_all.py) | The test suite (standard library only) — run it after any change |
| [`HOW_IT_WORKS.md`](HOW_IT_WORKS.md) | Walkthrough of the mechanics, from tokenising to sampling |
| [`data/input.txt`](data/input.txt) | Tiny Shakespeare (~1.1 MB), the corpus |
| `runs/` | Generated output: metrics, checkpoint, sample, loss curve (not committed) |

## Architecture

A decoder-only GPT, small enough to train on a laptop CPU:

Two sizes have been trained; both fit in the table below.

| Hyperparameter | Baseline | Larger |
| --- | --- | --- |
| Parameters | 816,128 | 2,702,208 |
| Layers | 4 | 6 |
| Attention heads | 4 | 6 |
| Embedding width | 128 | 192 |
| Context window | 64 characters | 64 characters |
| Vocabulary | 65 characters | 65 characters |
| Dropout | 0.1 | 0.1 |
| Optimiser | AdamW, betas (0.9, 0.95), weight decay 0.1 | same |
| Learning rate | 3e-4, constant | 3e-4, constant, then warmup→cosine decay to 3e-5 when resumed |
| Batch size | 16 | 16 |

Token and position embeddings feed four pre-norm transformer blocks
(`x + attn(ln(x))`, then `x + mlp(ln(x))`), then a final layer norm and a linear
head projecting to the character vocabulary. Loss is cross-entropy in nats per
character; a uniform guess over 65 characters would score 4.17.

## Setup

The environment is a Python 3.12 virtual environment. It was created with
[`uv`](https://docs.astral.sh/uv/), which needs no root access:

```bash
uv venv --python 3.12 .venv
uv pip install torch --index-url https://download.pytorch.org/whl/cpu
```

The CPU build of PyTorch is deliberate — there is no CUDA device on this machine.

## Train

```bash
.venv/bin/python train.py --max-iters 2000
```

Useful flags: `--batch-size`, `--n-layer`, `--n-embd`, `--block-size`,
`--eval-interval`, `--lr-schedule` (`cosine` or `const`), `--warmup-iters`,
`--min-lr`, `--checkpoint-interval`, and `--max-seconds` (a hard wall-clock
budget so a run can never run away). Progress is appended to
`runs/metrics.json` at every evaluation, so a run can be watched from outside
while it is still going.

The learning rate follows a linear warmup and then a cosine decay, and the
schedule spans the whole life of the model rather than a single session: a
resumed run continues its decay from where it left off instead of jumping back
to the peak rate.

Outputs written to `runs/`:

- `metrics.json` — config, full loss history (including the learning rate at
each evaluation), final statistics, sample
- `loss_curve.csv` — `step,train_loss,val_loss`
- `model.pt` — weights, optimiser state, character vocabulary and the loss
history so far; rewritten every `--checkpoint-interval` steps
- `sample.txt` — text generated by the trained model

### Continue a run

A checkpoint carries everything needed to pick the run back up — weights,
optimiser moments, step count, best validation loss and the loss history — so a
long run can be split across several short sessions, which matters on a machine
that throttles under sustained load:

```bash
.venv/bin/python train.py --resume runs/model.pt --out-dir runs_v3 \
    --max-iters 1600 --max-seconds 2400
```

`--max-seconds` bounds each session, not the model's total training time. The
loss curve stays continuous across the seam, and `runs/metrics.json` records
`prior_steps` and `resumed_from` so it is clear where one session ended and the
next began. The checkpoint is written to a temporary file and renamed, so an
interrupted run can never truncate the last good one.

## Tokenizers

Two tokenizers can be trained against, and the choice is not cosmetic.

| | `--tokenizer char` | `--tokenizer bpe` |
| --- | --- | --- |
| Unit | one token per character | byte-level subwords |
| Vocabulary | 65 | 512 (set with `--bpe-vocab-size`) |
| Corpus | 1,115,394 tokens | 575,345 tokens (**1.94 chars/token**) |
| 64-token context | 64 characters | ~124 characters |

[`bpe.py`](bpe.py) learns the merges from scratch — 256 byte symbols, then the most
frequent adjacent pair is merged, repeatedly, until the vocabulary is the size
you asked for:

```bash
.venv/bin/python bpe.py --vocab-size 512 --out runs_bpe/tokenizer.json
```

It prints the longest tokens it learned (` shall`, ` there`, ` would`, ` thou`),
verifies that encoding and decoding round-trip exactly, and shows how a sample
line is split. Training it on this corpus takes about 30 seconds.

Then train against it, and reuse the same file on later runs:

```bash
.venv/bin/python train.py --tokenizer bpe \
    --bpe-tokenizer runs_bpe/tokenizer.json --out-dir runs_tok_bpe
```

### Comparing across tokenizers

**Loss per token is not comparable between these two**, and neither is
perplexity. A token is about two characters of text under BPE, and a uniform
guess costs `ln 65 = 4.17` nats in one case but `ln 512 = 6.24` in the other, so
the same number means different things in each. Bits per character is the unit
that survives the change:

```
bits per character = (loss in nats / ln 2) / characters per token
```

Every run records `chars_per_token` and `val_bits_per_char`, and the chart can be
plotted on that axis instead:

```bash
.venv/bin/python render_curve.py --metric bits-char \
    --metrics runs_tok_bpe/metrics.json \
    --compare runs_tok_char/metrics.json --compare-label "char" \
    --baselines runs_bpe/bigram_baseline.json --out-dir runs_tok_bpe
```

`--metric bits-char` converts every series and every reference floor from its own
tokenizer, so a character-level and a subword run can share one chart. The
bigram floor can be measured on the same tokens:

```bash
.venv/bin/python bigram.py --tokenizer bpe --out runs_bpe/bigram_baseline.json
```

## Talk to it

```bash
.venv/bin/python chat.py
```

Loads `runs_tok_bpe/model.pt` by default and drops you into a prompt. A
checkpoint carries its own tokenizer, so any run can be used:

```bash
.venv/bin/python chat.py --checkpoint runs_v3/model.pt
.venv/bin/python chat.py --prompt "KING HENRY:" --max-new-tokens 200
.venv/bin/python chat.py --context 24        # hand the model a shorter window
.venv/bin/python chat.py --prompt "KING:" --stop $'\n' --stats
.venv/bin/python chat.py --checkpoint runs/does_not_exist.pt   # says so clearly
echo "To be or not" | .venv/bin/python chat.py
```

**It is a completion model, not an assistant.** Nothing here was
instruction-tuned, so asking it "what is 2+2?" gets the sentence continued in the
style of its corpus rather than answered. The prompt is built around that: you
type text, it continues it, and the running conversation stays in context for the
next turn. A blank line starts over from a newline, the same seed training uses.

Sampling is streamed token by token, and Ctrl-C stops a reply without leaving.
On this CPU it generates at roughly 58-113 tokens/second (the range measured
across replies here), so a 160-token reply takes a couple of seconds. Very short
replies report a lower rate: starting up costs about as much as the next twenty
tokens.
`--stop <text>` ends a reply when that text appears, which is the practical way
to get one speaker's turn and nothing else.

| Control | Effect |
| --- | --- |
| `/temp <f>` | temperature — lower is safer, higher is wilder |
| `/k <int>` | top-k cutoff; `/k 0` disables it |
| `/p <f>` | nucleus (top-p) cutoff, off by default |
| `/penalty <f>` | repetition penalty; 1.0 disables it |
| `/len <int>` | tokens per reply |
| `/seed <int>` | reseed the sampler (same seed, same text) |
| `/window <int>` | how many tokens of the end of the text to give the model; its `block_size` is the ceiling |
| `/context` | what the model will see next, how full it is, and how much of it the model has gone past |
| `/tokens <text>` | how the tokenizer splits a line — subwords are visible this way |
| `/reset`, `/save <file>`, `/help`, `/quit` | as they sound |

The same knobs are flags (`--temperature`, `--top-k`, `--top-p`,
`--repetition-penalty`, `--max-new-tokens`, `--seed`, `--stop`, `--context`) for
one-shot use. `--context` is the same window setting the browser's control
moves: a smaller number is a handicap you choose, and the model keeps writing
with less to go on.
There is a browser front end for the same prompt — see
[Talk to it in a browser](#talk-to-it-in-a-browser) below.

## View the loss curve

```bash
.venv/bin/python render_curve.py
```

This writes `runs/loss_curve.svg` and a self-contained `runs/loss_curve.html`
that includes the generated sample. Open the HTML file in any browser. The chart
overlays the learning rate on a right-hand axis and marks where a resumed run
picked up.

`--run "label=path/to/metrics.json"` adds a row to the runs table, and can be
repeated. `--compare path` overlays another run's validation curve:

```bash
.venv/bin/python render_curve.py \
    --metrics runs_v3/metrics.json \
    --baselines runs/bigram_baseline.json \
    --compare runs_baseline/metrics.json --compare-label "816K baseline" \
    --run "816K, 4 layers=runs_baseline/metrics.json" \
    --run "2.7M, constant lr=runs/metrics.json" \
    --run "2.7M, resumed with cosine decay=runs_v3/metrics.json"
```

## Talk to it in a browser

```bash
.venv/bin/python serve.py                       # then open http://127.0.0.1:8765/
.venv/bin/python serve.py --checkpoint runs_v3/model.pt --port 9000
.venv/bin/python serve.py --open                # open the page for you
```

One standard-library process: no framework, no build step, no new dependency.
It serves a single self-contained page (inline CSS and JS) and a small JSON API.
Sampling is not reimplemented — the server calls the same `stream_reply` that
`chat.py` does, so the browser, the terminal prompt and training-time sampling
are one code path, and the page says so.

Tokens appear as they are sampled, not when the reply ends. The server writes
newline-delimited JSON over chunked transfer encoding, and the page appends each
chunk as it arrives:

```
{"t": "meta",  ...}                        what the reply is being made with
{"t": "chunk", "text": "..."}              text to append, as it is sampled
{"t": "done",  "text": ..., "steps": 8, "seconds": 0.6, "in_context": 41, ...}
{"t": "error", "message": "..."}           mid-stream, after the headers
```

NDJSON over `fetch` rather than Server-Sent Events, because `EventSource` cannot
POST the settings along with the prompt — and a `TextDecoder` over a stream is a
smaller cost than marshalling the request through a query string.

`done` also carries the two counts that make the context window honest.
`in_context` is every token written, but the model only reads the last
`block_size` of them: `dropped_tokens` is how many ended up outside the window,
and `dropped_prompt_tokens` is how many of the prompt alone never reached it. A
prompt longer than the window is the quiet case — without those numbers the page
would look as though the model had read all of it.

`boundary_chars` is the third piece of the same story: where that window begins,
as a character offset into the transcript the model was given, or `null` when the
offset cannot be placed in the text. It is measured from the visible tail rather
than from the dropped prefix, because a byte-level token can cut a multi-byte
character in half and the two ways of slicing then disagree by exactly that
character.

**The controls are the sampling controls**, wired to the same names the CLI uses:
temperature, top-k (0 disables it), top-p with an on/off toggle, repetition
penalty and its window, max new tokens, a stop string, and a seed. Four presets
— Default, Steady, Wild, Greedy — set them together. Because the server seeds
torch per request, a fixed seed makes a reply reproducible: the same text and the
same seed give the same continuation, which is what makes the page testable.

One control is not a sampling control: **Context** sets how many tokens of the
end of the text the model is actually given. `block_size` is what the checkpoint
was trained for and therefore a ceiling, not a requirement — the positional
embeddings cannot address more — so the control only ever shortens the window.
Dragging it moves the line in the transcript at once, without generating
anything, so the boundary is something you can watch travel up and down a
transcript while the replies lose the thread around it. Lower it far enough and
even the text you just typed partly falls outside.

Two conveniences worth knowing: **Stop** aborts a reply and keeps the part that
was already sampled, and **Tokens** shows how the tokenizer split the current
text into subwords (`the king` → `t | he | k | ing`), which is the browser's
version of `/tokens` in `chat.py`.

The window is stated rather than implied. A line under the title reads
`context window: 28/64 tokens in view`, and turns amber once the transcript is
longer than the model can read: `the last 64 tokens are what the model reads —
284 of 348 written are out of view`. When the prompt alone overflows it says so
in words — the opening of what you typed was never read. In the token view the
chips that have fallen out of the window are dimmed and dashed, so "what does
the model actually see" is something you can look at rather than infer.

The transcript carries the boundary itself. Once the window overflows, a dashed
rule appears where the model's memory begins — `outside the model's window · 730
tokens above` — and everything above it is dimmed, so the line between what the
model reads and what it has forgotten is a place on the page rather than a number
to hold in your head while reading. The offset is exact: the characters below the
line tokenise to precisely `block_size` tokens. Two things it deliberately does
not do. It is drawn only for a *completed* reply, because an abandoned one leaves
no boundary that was ever computed — and a line in the wrong place is worse than
no line. And its label is a CSS pseudo-element rather than text, because the
document's text is the transcript the next prompt is built from and that Copy
puts on the clipboard.

It binds to `127.0.0.1` by default. It serves whatever checkpoint you point it at
to anyone who can reach the port, so the flag is there if you want it elsewhere.
Loading a checkpoint takes a few seconds on this CPU, and the socket is not bound
until that finishes — the banner says so rather than leaving you refreshing.

## Tests

```bash
.venv/bin/python test_all.py            # the whole suite, about 90 seconds
.venv/bin/python test_all.py TestBPE    # just one class
```

The suite runs on the standard library alone — no pytest — and covers the
properties the numbers above depend on — each of which has broken at least once,
and would quietly invalidate the results if it broke again:

- a BPE round-trip is lossless (including non-ASCII), deterministic, and the
  encoder never stops with a known merge still adjacent
- a checkpoint rebuilds the exact vocabulary its weights were trained against,
  including the legacy `itos`/`stoi` checkpoints written before the tokenizer
  was pluggable
- `sample_next` matches an independently written reference of its documented
  rules for every control, `top_k <= 0` disables the cutoff instead of crashing,
  and `generate` is exactly a loop over `sample_next`
- the bigram floor is measured on the same validation split as the model, so the
  two can honestly share one bits-per-character axis
- a resumed run keeps its history, records no duplicate point at the seam step,
  and does not jump back to the peak learning rate
- the web server serves a self-contained page, streams NDJSON chunks over
  chunked framing, rejects bad settings with a reason, and stops a reply when the
  browser walks away instead of sampling on into a dead socket
- the window arithmetic the page reports is exact: a prompt of exactly
  `block_size` tokens drops nothing and one token more drops one, with the counts
  cross-checked against an independent `/api/tokens` encode
- the token view cannot be squeezed out of its own height: the layout contract
  that keeps it visible is resolved from the stylesheet the server actually
  sends — who shrinks, who caps, who yields — and the check is shown to fail on
  the layout that once collapsed the panel to about twelve pixels
- the window can be deliberately shortened but never stretched past what the
  checkpoint was trained for, and the crop is pinned where sampling noise cannot
  mask it — on the width of the tensors the model is actually handed — alongside
  a check that the preview the control asks for is exactly what a reply of the
  same window reports
- the edge of the model's window is a real place in the text, not a close one:
  the offset is cross-checked by slicing the same tokenisation two ways, holds
  for both tokenizers, and lands before the character when a byte-level token
  cuts one in half — and an offset that cannot be placed is refused, not guessed
- the label on that line cannot join the transcript: it comes from a
  pseudo-element, so the document's text stays exactly what the next prompt is
  built from and what Copy copies

## Results

Trained on this machine — CPU only, no GPU, no pretrained weights. Three runs,
same corpus, same context window and same batch size:

| Run | Params | Steps | Wall clock | Val loss | Perplexity |
| --- | --- | --- | --- | --- | --- |
| Baseline | 816,128 | 1,534 | 600 s | 2.0495 | 7.76 |
| Larger | 2,702,208 | 2,673 | 2,400 s | 1.8249 | 6.20 |
| **Larger, resumed with cosine decay** | **2,702,208** | **4,206** | **4,801 s** | **1.7018** | **5.48** |

Every run stopped at its wall-clock budget rather than converging, so these are
where each got to in the time available, not the models' limits. Tripling the
parameters and quadrupling the time bought **0.225 nats**. The third run is the
second one *continued*: same weights, same batch size, same peak learning rate,
with the constant rate replaced by a warmup-then-cosine-decay schedule. That
change alone is worth a further **0.123 nats** — and unlike the first two, it
finishes with its learning rate at the floor, having actually settled.

| What changed | Val loss |
| --- | --- |
| 816K params | 2.0495 |
| 3.3x the parameters | 1.8249 |
| + cosine decay instead of a constant rate | **1.7018** |

The earlier runs are kept in `runs_baseline/` and `runs/` so all three curves
can be drawn together.

### How it compares

| Model | Val loss (nats) | Perplexity |
| --- | --- | --- |
| Uniform — guess any of the 65 characters | 4.1744 | 65.00 |
| Bigram — sees only the previous character | 2.4838 | 11.99 || **Transformer** — sees 64 characters | **1.7018** | **5.48** |

Context and attention are worth **0.782 nats** over the bigram floor.

### Character-level vs subword

A matched pair: identical model, batch size, context length, learning-rate
schedule and step budget — the only difference is the tokenizer. Both reached
1,000 steps and both finished with the learning rate at its floor.

| Run | Vocab | Params | Steps | Val loss | Perplexity | Bits/char |
| --- | --- | --- | --- | --- | --- | --- |
| Character-level | 65 | 2,702,208 | 1,000 | 2.1774 nats/char | 8.82 | 3.1413 |
| **Byte-level BPE** | **512** | **2,873,856** | **1,000** | **3.5878 nats/token** | **36.15** | **2.7269** |

Loss per token and perplexity are **not** comparable across these rows — a BPE
token is about two characters of text, and a uniform guess costs `ln 512 = 6.24`
nats under BPE but `ln 65 = 4.17` under characters. Bits per character is
computed from each run's own `chars_per_token` and is the only number that means
the same thing in both rows: **2.73 vs 3.14, a 13% improvement from the
tokenizer.**

The gap is stable rather than an artifact of where the runs happened to stop:

| Step | Char-level | BPE-512 | Gap |
| --- | --- | --- | --- |
| 800 | 3.1860 | 2.7531 | +0.4329 |
| 850 | 3.1677 | 2.7458 | +0.4219 |
| 900 | 3.1601 | 2.7428 | +0.4173 |
| 1,000 | 3.1274 | 2.7232 | +0.4042 |

(validation bits per character, from each run's own evaluation points)

**Two caveats, both cutting against the subword run**, so treat ~0.42 bits/char as
a conservative estimate rather than a measured effect:

- The character run reached 1,000 steps in two sessions, and the second one
  omitted `--batch-size`, so its last 150 steps ran at batch 32 instead of 16.
  From step 850 on it saw *more* tokens per step than the subword run, which is
  why the gap narrows slightly in the table above; up to step 850 the two are
  matched exactly.
- At equal *steps* a subword model has read more text: 1,000 steps is 1.74
  passes over the corpus versus 0.92 for characters.

What is structural rather than measured is that a subword model needs ~1.94x
fewer steps to cover the same text. Wall clock says nothing here — this machine's
speed varied by roughly 5x between the two sessions (2,496 tokens/s measured for
the character run against 530 for the subword one, while the character run was
simply running during a faster spell).

The more interesting result is what happens to the *floor*:

| Model | char-level | BPE-512 |
| --- | --- | --- |
| Uniform | 6.0224 | 4.7416 |
| Bigram — one token of history | 3.5834 | 2.7768 |
| Transformer — full context window | **3.1413** | **2.7269** |
| Attention's gain over its own bigram | **0.4421** | **0.0499** |

(all in bits per character, lower is better)

Switching the unit from characters to subwords improves the *trivial* bigram by
**0.807 bits/char** — more than the 0.442 that the whole transformer buys over a
bigram at the character level. And the BPE transformer is only 0.05 bits/char
above BPE's own bigram, while the character transformer sits 0.44 below its.

The reading: at the character level the model has to learn from scratch that `q`
precedes `u` and `t`,`h`,`e` come in that order; a subword vocabulary hands it
most of that for free, so there is much less left for attention to discover on
this corpus. Character-level modelling is the harder problem, and it is where the
architecture earns its keep. This is one corpus at one size with a single run per
configuration, so treat the sizes of these effects as indicative, not measured.

It has learned speaker names in capitals (`HENRY BOLINGBROKE`, `TRANIO`),
line breaks, punctuation and the shape of English words — `crown`, `soul`,
`willow` and `speach` are all recognisable, and `Why,` opens a line the way
Shakespeare does. It has **not** learned to be coherent — expected for ~2.7 M
parameters trained for eighty minutes on a CPU.

The difference is qualitative, not just numerical. The subword run produces whole
English words — `myself`, `loved`, `thou`, `night`, `sir` — where the

it is the same reason the tokenizer improves the bigram floor too.
